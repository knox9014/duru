# duru v0.1 축소 스펙

> 원본: `Markdown Document IDE 개발 계획서.md`
> 그 계획서를 **4~6주 안에 끝나는 크기**로 자른 것.
> `duru` 는 코드네임. 제품명은 5주차에 확정.

---

## 0. 전제

**최우선 가치는 "워드처럼 쉬운 편집"이다.** 마크다운을 전혀 모르는 사람이
메뉴에서 표를 삽입하고, 칸을 클릭해서 입력하고, 굵게 버튼을 누를 수 있어야 한다.
화면에 `|` 나 `**` 같은 기호가 보이면 실패다.

Git·검색·AI 는 그 다음이다. 이 순서를 뒤집으면 v0.1이 아니다.

타깃은 "개발자 옆 사람" — 기획자, 조교, 테크라이터.
회사 문서를 AI에 넣으려고 정리하는 사람도 여기 들어간다.

---

## 1. v0.1이 증명해야 하는 것 — 단 하나

> **워드처럼 편집해도, 문서에 있던 것이 하나도 사라지지 않는다.**

워드식 편집기는 자기가 모르는 요소를 **조용히 삭제한다.** 사용자는 화면에서
안 보였으니 알아채지 못하고, 되돌릴 수도 없다. 이게 이 제품을 죽일 수 있는
유일한 결함이다.

v0.1의 모든 결정은 이 문장을 지키기 위해 존재한다.

## 2. 기술 결정

| 영역 | 선택 | 이유 |
|---|---|---|
| 셸 | Tauri 2 | 파일 직접 접근, 번들 작음 |
| UI | React + TypeScript | 생태계 |
| 글자 입력 | **ProseMirror** | 한글 조합(IME), 커서, 실행취소. 직접 못 만듦 |
| 마크다운 해석 | **remark / unified** | CommonMark 명세는 직접 구현 대상이 아님 |
| 그 사이 변환 | **직접 구현** | §2.3 때문에 소유해야 함. Milkdown 안 씀 |
| Git | 시스템 `git` 호출 | `status`/`diff`/`add`/`commit` 4개 |

### 2.1 "파일이 지저분해진다" 문제 — 정규화로 해결

ProseMirror 계열은 저장할 때 문서를 자기 방식으로 다시 쓴다.
그대로 두면 한 글자만 고쳐도 파일 전체가 바뀐 것으로 기록된다.

**해법: 처음 열 때 한 번 전체를 정규화해서 저장한다.**

```
1회차  열기 → 전체 정규화 → 저장   (여기서 한 번 크게 바뀜)
2회차  한 단어 수정 → 저장          → 그 줄만 바뀜
3회차  이후 계속 동일
```

직렬화가 결정론적이므로, 안 건드린 부분은 바이트까지 동일하게 재생산된다.
코드 포매터를 도입할 때 첫 커밋만 크고 이후가 조용한 것과 같은 원리다.

- 앱 도입 시 **"전체 정리" 커밋 1회**를 안내한다. 이건 버그가 아니라 절차다.
- 외부 도구로 고친 파일을 다시 열면 재정규화가 일어난다. 정상 동작으로 본다.

### 2.2 쓰지 않는 것

**CodeMirror 하이브리드** — 파일을 전혀 안 건드리지만 표가 `| a | b |` 로 보인다.
§0을 만족하지 못한다. 파일 청결이 편집 경험보다 앞설 수 없다.

**Milkdown** — ProseMirror + remark 조합을 이미 갖춰줘서 시작은 빠르다.
그러나 변환 계층을 Milkdown이 소유하므로 §2.3을 끼워넣기 어렵다.
v0.1의 핵심 과제가 바로 그 계층이라 래퍼가 방해가 된다.

**직접 짜지 않는 것 (중요)** — 마크다운 파서 자체. CommonMark 명세 구현은
몇 달짜리 작업이고 우리가 얻을 게 없다. remark를 쓴다.

### 2.3 소실 방지 — v0.1의 핵심 구현 과제

편집기가 이해하지 못하는 요소는 삭제된다. 이를 막기 위해:

**모르는 것은 "손대지 않는 덩어리"로 통째 보존한다.**

remark 는 각 노드가 원본의 몇 줄~몇 줄인지(`position`)를 함께 준다.
이게 해법의 열쇠다.

```
원본                     remark 결과
────────────            ──────────────────
1  # 제목                heading   1~1
3  <details>             ???       3~7   ← 원문 3~7줄을 통째로 보관
7  </details>
8  본문                  paragraph 8~8
```

- 스키마에 없는 노드는 `position` 으로 원문을 잘라 문자열째 보관
- 화면에는 회색 상자로 "원본 유지 영역" 표시 (편집 불가, 삭제도 불가)
- 저장 시 그 문자열을 같은 자리에 그대로 되돌림 — 손댄 적이 없으므로 소실 불가

대상: raw HTML, 각주, frontmatter, 위키링크, 참조식 링크 정의, 정의 목록 등.

> 이게 v0.1에서 가장 어려운 부분이다. 여기에 시간을 쓴다.

## 3. 범위 — 넣는 것

### 3.1 파일 / 워크스페이스
- 폴더 열기 (하나)
- 좌측 파일 트리 — `.md` / 이미지만
- 파일 생성 / 이름 변경 / 삭제, 탭
- 저장(Ctrl+S) + 자동 저장(5초 idle)
- UTF-8 고정, 개행 코드 유지
- 외부 변경 감지 후 재로드 확인

### 3.2 에디터 — 여기가 제품이다
화면에 마크다운 기호가 **보이지 않는다.**

- 제목 1~4 (드롭다운으로 선택)
- 굵게 / 기울임 / 취소선
- 목록, 번호 목록, 체크박스 (탭으로 들여쓰기)
- 인용
- **표** — 삽입, 칸 클릭 입력, 행/열 추가·삭제, 탭 이동
- 링크 (대화상자), 이미지 (붙여넣기·드래그 시 `assets/` 자동 복사)
- 코드 블록 (언어 선택)
- 수평선
- 붙여넣기 시 서식 유지

### 3.3 메뉴 / 툴바
```
파일   편집   삽입   서식   보기
[제목 ▼] [B] [I] [S] │ [목록] [번호] [☑] │ [표] [링크] [이미지] [코드] [인용]
```

### 3.4 모드 전환
```
[ 문서 ]  [ 원본 ]
```
원본 모드는 개발자용 확인 창. 편집도 되지만 v0.1에선 부가 기능.

### 3.5 Git (버튼 4개)
| UI | 내부 |
|---|---|
| 변경된 문서 (N) | `git status --porcelain` |
| 변경 내용 보기 | `git diff -- <file>` |
| 버전 저장 | `git add` + `git commit -m` |
| 기록 | `git log --oneline -- <file>` |

`git` 없으면 패널을 숨기고 순수 편집기로 동작.
**없음:** push/pull/branch/merge/충돌 해결.

### 3.6 기타
찾기·바꾸기 · 실행취소 · 단축키(Ctrl+B/I/K/S/F/Z/Y)

### 3.7 모드 · 테마
- **문서 모드 / 작업실 모드** 전환 (첫 실행 시 선택, 설정에서 변경)
- **밝게 / 어둡게 / 시스템 설정** 전환
- 상세: `duru/MODE_PLAN.md`

### 3.8 지원 서식의 범위
워드 서식 중 무엇을 만들 수 있고 무엇이 보존만 되는지: `duru/FEATURE_MAP.md`
- 밑줄은 `<u>` 로 지원 (유일한 예외)
- 글자색·형광펜·정렬·글꼴은 지원하지 않고, `서식` 메뉴에서 이유를 안내

## 5. 완료 판정

### G1. 소실 0 — **최우선**
`duru-torture.md` 를 열고 저장한 뒤, 원본과 비교해 **사라진 요소가 하나도 없어야 한다.**
표현 방식이 바뀌는 건 허용(§2.1). **내용이 없어지는 건 불허.**

특히 확인: raw HTML, `<details>`, 각주, frontmatter, 참조식 링크, 위키링크,
줄 끝 공백 2칸(강제 개행), 코드블록 내부 문자열.

### G2. 두 번째 저장부터 무변경
```
1회차 저장  → 정규화로 크게 바뀜 (정상)
2회차 저장  → git diff 완전히 비어야 함
```
2회차에서 한 줄이라도 뜨면 실패.

### G3. 최소 수정 = 최소 변경
정규화 이후, 한 단어만 고치고 저장 → `1 insertion(+), 1 deletion(-)`

### G4. 표 편집이 워드 같은가
마크다운을 모르는 사람에게 시켜본다. 설명 없이
표 삽입 → 칸 입력 → 행 추가를 해내면 통과. **화면에 `|` 가 보이면 실패.**

### G5. 상호운용
만든 문서가 GitHub / VS Code / Obsidian 에서 정상 렌더링.

### G6. 성능
5,000줄 문서에서 타이핑 지연 체감 없음.

## 6. 의도적으로 미해결로 남기는 것

**댓글 / 변경 추적을 안 넣는 이유는 시간이 아니라 모순 때문이다.**
별도 파일에 위치 기반으로 저장하면, 그 문서를 다른 앱에서 한 번만 고쳐도
위치가 전부 어긋난다. 그런데 원본 §30은 "다른 프로그램에서 즉시 사용 가능"을
원칙으로 못박았다. 둘 다 가질 수 없다. 설계 답이 나오기 전엔 만들지 않는다.
